## Decisions (defaults set 2026-10-24; Xander can overrule)

| # | Decision | Why |
|---|---|---|
| Q1 | **Each backend's queue lives where it can be controlled.** *Revised 2026-10-24 after Xander asked "shouldn't the lab server own the queue?" — yes, for the desktop.* **Local: the desktop job server owns its queue** (its SQLite queue, already built): WZRD submits a local job as soon as the server is reachable; ordering, reorder and position come from the server (new additive routes, lane L). The hub only holds a local job while the server is unreachable (phase `waiting_backend`), then submits it. **Modal: the hub owns the queue** — one ordered lane, a job is spawned only when a slot is free. **Slots = an operator setting, default 1, range 1–3** (Xander 2026-10-24: a UI slider for how many GPU containers may run at once; persisted in `library.db` `settings`, `TEXTUREFLOW_MODAL_SLOTS` only seeds it; the ceiling is the app's `max_containers` = 3 — raising it is a lab change Xander must approve). Lowering it never cancels running jobs; they finish and the lane drains to the new limit. | Desktop: the queue survives the laptop closing / a hub restart mid-gig, inputs are already uploaded when the GPU frees, GPU sharing with lab batches is decided in one place, and the server sees every client's jobs. Modal: a spawned call can't be reordered, so jobs beyond the slots must wait somewhere we control. |
| Q2 | **Manual routing only.** The operator picks the backend per render (Render panel toggle, default remembered); a *queued* job can be moved to the other lane by hand. Never auto-route, never fall back on failure (standing decision). A finish (`finish_from`) is pinned to its draft's backend and can't move. | Lab + WZRD standing rule; the bundle lives on the backend that rendered the draft. |
| Q3 | **The server stays up; its GPU worker comes and goes.** The systemd service (linger on) is a light aiohttp process (never imports torch) and always runs. Its GPU worker boots when a job is queued and **exits after `TFLAB_WORKER_IDLE_S` (default 600 s) with an empty queue**, releasing `gpu.lock` and VRAM; health reports `worker: idle` then (new value; WZRD treats it as up). The hub needs SSH (`TEXTUREFLOW_LOCAL_SSH=rednax-beast`, `/usr/bin/ssh -o BatchMode=yes`, lab script `textureflow-ctl status\|start`) only when the desktop answers SSH but the service doesn't (crashed / not started): it runs `start` then, at most once a minute while local jobs wait. Desktop off = lane **off**, jobs held in the hub, nothing fails. No Wake-on-LAN. | "When that machine is on, the client can start the server." Idle release hands the GPU back to lab work without WZRD having to stop anything. |
| Q4 | **GPU contention: the server waits, lab batches yield between renders.** When the worker must boot and `gpu.lock` is held by another process, the server touches `$TFLAB_STATE/gpu.want` and waits (health `worker: waiting_gpu`, `gpu_holder` = the holder's command); jobs stay queued, never fail, and these waits don't count toward the 3-boot-failures → `down` rule. `tools/local_batch.py` (incl. `--watch`) checks `gpu.want` between renders, releases the lock and waits until the file is gone; the worker removes `gpu.want` when it exits idle. | "Push jobs to it when the GPU is free" without ever killing someone else's render (lab rule). |
| Q5 | **Modal progress via a side channel:** `TextureFlow.render(args, files, progress_key=None)` (additive kwarg) writes `{stage, step, total, t}` to Modal Dict `textureflow-progress` (env `wzrd`), throttled ≥ 1 s except stage changes. The deployed `spec()` reply gains `capabilities: ["progress_dict"]`; WZRD passes `progress_key` only when its cached `spec()` lists it (the fallback app and older deploys get nothing → estimate-only bar). | `spawn` is opaque; a Dict is the cheapest Modal-native channel and keeps `render`'s response untouched. |
| Q6 | **ETA = stage model × history.** Hub `tf_eta.py` predicts per-stage seconds from the args (frames × first-pass pixels × steps for sampling; output pixels × frames for upscale/ESRGAN/RIFE/encode) per GPU, seeded from the lab's measurements (3090: the 104 explore-batch-01 result JSONs on the desktop carry `params` + `stage_s`; Modal RTX PRO 6000: lab `docs/reference/benchmarks.md`) and refit from WZRD's own records. Live: done stages' predicted time + the running stage × `step/total` (or elapsed/predicted, capped at 95 %) → `pct`; remaining time is rescaled by the job's observed speed ratio. Queued jobs show the sum of predictions ahead ÷ slots. | "Won't be perfect, that's alright": a stage-aware bar beats a median; it improves as records accumulate. |
| Q7 | **Records keep `info.stage_s`, `info.gpu`, first-pass + output size and `timings`** under `record.textureflow` from now on (the estimator's training data, and the lab's preference dataset). | Today WZRD drops `info` except stage/draft. |
| Q8 | **Hub restart:** local jobs already submitted keep rendering on the server; on hub start the hub re-adopts its own unfinished local jobs (job rows carry the server job id) and collects their results. Modal jobs still queued in the hub read `lost` (persisting the Modal lane is an open item). Queued or running jobs keep the hub from idle exit. | The desktop queue is durable now (Q1); the Modal lane stays the small first cut. |
